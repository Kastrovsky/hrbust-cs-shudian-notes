# Skill Router（技能路由）

## Overview

目的只有一个：**先匹配，再动手**。

用户机器上装了多种专用技能（课程整理、手写笔记、公式审计、文献检索、雅思口语……），每个技能都固化了特定工作流、校验脚本和输出格式。不加载技能直接做，结果往往"能用但不合规矩"——格式不对、漏了校验、与历史产出一致性断裂，用户得再提一轮修改。匹配正确则一次做完。

反过来，**不该加载时不加载**：技能会注入大量上下文，简单问答套技能反而变慢。所以本技能的核心是一张判定表，不是一个"强制全加载"的开关。

## 五步流程

0. **时序**：这一步必须在**调用任何其他工具之前**完成。判断依据是用户这句原话本身，不是"我以为我要做什么"——先想清楚再去找技能，等于已经开干了。

1. **读表**：看下面「路由表」，按用户这句话的**动作 + 对象**找行，不按关键词字面匹配。拿不准或一句话里混了多个领域时，直接跑匹配器，别硬猜：

   ```bash
   python "<技能目录>/scripts/match_skill.py" "用户的原话"
   ```

   它按「触发词」小节打分，返回前 3 个候选、得分和命中的词。输出"无匹配技能"就是真的没有，走通用能力。
   **自动挡（2026-11-12 装）**：`~/.workbuddy/settings.json` 的 `hooks.UserPromptSubmit` 挂了 `scripts/on_prompt.py`，每条用户消息提交时自动跑一次匹配，命中就以 `<skill-match>` 标签注入「建议加载 X」。看到这个标签＝第 1 步已经做完，直接进第 3 步加载，别重复跑脚本；标签不存在（闲聊／无匹配／钩子未生效）才手动跑上面的命令。钩子只提示、不替你判定；无匹配与异常都静默放行，**改完 settings.json 要完全退出并重启 WorkBuddy 才生效**。安装器 `scripts/install_hook.py` 幂等，换机器或配置被重置时重跑一次即可。
2. **判定**：命中 → 加载；未命中 → 走通用能力，直接做。
3. **加载**：用 Skill 工具加载命中的技能，然后**严格按其工作流执行**（含它的校验脚本、命名规范、提交方式）。
4. **报备**：一句话说明"按 X 技能执行"，让用户知道你用了哪套流程；未命中时也可说明"无匹配技能，按通用流程处理"。
5. **交付即自检**（默认动作，不等用户提）：每个带明确指令的任务交付完，跑 `scripts/selftick.py --tick` 计数，同时过一遍「沉淀判定」——命中且三问全中就**直接落地**（新建技能／优化现有技能／写记忆），末尾一行告知，**不先问**。本会话累计满 5 个任务（或同一件事 ≥30 轮）时 `selftick` 会提示做模式扫描。判据见「沉淀判定」。

判定失败的三种典型情形，务必回表重判：

- 用户只说了对象没说动作（"这个 PPT"）→ 看上下文推断动作，或直接问一句。
- 用户用了简称（"老规矩""按之前的流程"）→ 结合仓库/历史产出推断，通常是上一次用过的技能。
- 一条指令里有两个子任务（"整理这章笔记然后推送"）→ 拆开分别匹配，见「组合规则」。

## 「每次都要」是机制需求，不是一次性任务

用户说「每次任务前都要…」「确保每次都…」「以后都这样」「别再漏了」时，**别只把这一次做对**——他在描述一种反复出现的行为，要做的是让它不依赖记性。

| 诉求里的词 | 真正要做的 |
|---|---|
| 每次 / 都要 / 以后都 | 检查有没有 hook、脚本、技能或记忆条目能承载它 |
| 确保 / 别再漏了 | 加可验证的检查（回归用例、清单存档、复跑确认） |
| 正确地 | 加防护规则（黑名单、dry-run、先出清单再动手） |

判断顺序：**机制 > 记忆 > 自觉**。能写成脚本或 hook 的，不要写成"我以后注意"；只能靠判断的，写进 `MEMORY.md` 并给出可执行的判定步骤。

两个真实例子：用户说「每次任务前必须自动查找合适的 skill」，落地不是"我下次记得跑"，而是 `on_prompt.py` 这个 `UserPromptSubmit` hook 加留痕日志；用户说「确保临时产物每次都能正确删除」，落地不是再删一遍，而是 `tmp-hygiene` 技能——分类规则加默认 dry-run。

## 组合规则

一个任务需要多技能串联时，按"骨架 → 内容 → 校验 → 交付"排序，不要并行加载互斥技能。

| 场景 | 串联顺序 |
|---|---|
| 课程仓库大改 | `course-study-kit`（定章节骨架）→ `handwritten-study-notes`（写内容）→ `math-formula-audit`（查公式）|
| 写论文 | `global-biblio-base`（找文献）→ `paper-reference-formatter`（规范条目）→ `workbuddy-docx`（成稿排版）|
| 雅思（四选一） | 课堂材料 → `ielts-class-notes`；每日对练/审题/改题型 → `ielts-speaking-drill`；词表出练习题 → `ielts-wordbank-drill`；建词条素材库 / 写 7 分范文 → `ielts-material-bank`。四者互斥，按**产物形态**判定，不看关键词；词表技能出题时也须遵守 `ielts-speaking-drill/references/question-types.md` |
| 任何文档类交付 | 最后一步都是 `present_files` 展示成品，不是只回文字 |

## 优先级与冲突

1. **用户显式指定**（`@skill:xxx` 或"用 xxx 技能"）> 本路由表自动匹配。
2. **项目级技能**（`{项目}/.workbuddy/skills/`）> 用户级技能，同名时以项目级为准。
3. **专用技能 > 通用能力**：宁可加载一个 90% 贴合的技能，也不要用通用流程重造它的工作流。
4. **用户当次的新指令 > 技能里的旧约定**：技能是默认流程，用户明确要求变通时按用户说的做，并在回复里说明偏差。
5. **专用技能强命中 > 元技能兜底**：非 `skill-router` 技能得分达到 `STRONG_HIT`（30）时，说明用户明确指向某工作流，长句里的 "skill / 匹配" 只是附带词，兜底不再把 `skill-router` 顶到 top-1。

## 沉淀判定：什么时候该造新技能

路由管「**用哪个**」，本节管「**要不要造新的**」。闭环：造出来的技能必须回写路由表，否则下次照样匹配不到，白造。

**触发权在我这边，不在用户那边。** 用户不会主动说「做个技能」或「以后都这样」——他常常想不到这一层。我要在固定节点自己判断，判断完只在**有结论**时开口。完整细则与话术见 `references/distill-trigger.md`，候选台账见 `references/distill-ledger.md`。

### 三个触发时机（T1 必做，T2/T3 补漏）

| 时机 | 什么时候 | 干什么 |
|---|---|---|
| **T1 交付即检**（主时钟） | 每个带明确指令的任务交付完（改完文件、推完提交、交完稿） | 对**刚做完这一件事**跑一遍三问。默认动作，不是可选项 |
| **T2 累积巡检** | 同一会话累计满 **5 个任务**，或同一件事来回 **≥30 轮** | 扫**所有已完成任务**，找单次看不出的跨任务重复模式——同一套步骤做了三遍，就是该建了 |
| **T3 兜底巡检** | ① 用户说「结束 / 先这样 / 换个话题」或上下文即将压缩时扫一遍；② 每周日 21:00 的自动化「技能提取与创建巡检」（id `da4b19b2`）扫最近 7 天日志 | 整段对话兜底过一遍，防止长会话里的模式随压缩一起丢掉；定时那条没有对话上下文，只处理 ≥2 次独立出现、且查重结论明确的高置信模式 |

T2/T3 的计数**用磁盘状态记，不靠临场记性**：每完成一个任务跑一次 `scripts/selftick.py --tick`，累计满阈值它会自己提示做模式扫描（扫完 `--scanned` 清零）；会话第一个任务前跑 `--status`，报「距上次巡检 >7 天」就 `--audit`。真正的定时器在对话里做不到，所以：**会话内用任务数+轮次数等效（selftick 落盘），跨会话靠周日那条自动化兜底**。

**周日那条 2026-11-12 已从「只提候选」升级为「提取 + 真落地」**：三问全过、同一流程近 7 天 ≥2 次独立出现、且 `overlap_check.py` 查重结论明确时，它按「落地必做」链路真的把技能改好或建好（优化现有／合并／新建，含建实体 → junction → `quick_validate.py` → 四处注册 → 回归用例 → `refresh_index.py` + `--selftest` + `overlap_check.py all` → 台账），失败即回滚；证据不足才留候选区标「待判」。**它不改现有技能的既有流程段落**——没有对话上下文改那个容易出事，那是会话内 T1 的活。

### 三问（T1 每次都跑，30 秒内出结论）

1. **可复现**——换个输入物（另一本书、另一门课、另一批题、另一个仓库）还能跑？
2. **非显然**——装的是用户的偏好、我们踩过的坑、阈值、命名约定？只是「我会写文档」→ 通用能力，不建。
3. **边界清**——说得清什么情况**不**适用？

三问全过 → **默认直接落地**（新建或优化现有技能都直接动，见「怎么落地」）。有一条不过 → 下沉到该去的地方，**不建技能**。

### 加速信号（命中就更快下结论，不是闸门）

这些迹象说明「这次的东西值得留下」。出现任意两条即可直接下结论、进入落地：

| 信号 | 判据 |
|---|---|
| 用户给过明确规格 | 「以后都这样 / 按这个标准 / 必须… / 不要…」，且说的是一**类**任务 |
| 同一处往返 ≥3 轮 | 结构级修订，不含错别字 |
| 用户否掉了我的默认做法 | 并给了替代方案 |
| 同类返工 ≥2 次 | 一次任务里同类型错误出现两次以上 |
| 定稿与初版结构差异大 | 且每条改动理由能归成规律 |

**这些信号一个没出现，三问也可能全过**——比如这次任务本身就跑通了一套从没写下来的流程。所以别把它们当闸门，只当加速器。

### 四档落地：先归类，再新建

**顺序不能反**——默认假设"已经有技能能装下"，找不到证据才新建。技能库最怕的不是少一个，是三个技能抢同一批触发词，每次都要临时仲裁。

| 档 | 判定 | 动作 |
|---|---|---|
| ① 归类（首选） | 现有技能覆盖 ≥50%（跑 `overlap_check.py candidate` 看） | **改那个 SKILL.md**：补判据、补踩坑条目、扩「何时用」、加触发词。不新建 |
| ② 合并 | 两个技能重叠 ≥50%（`overlap_check.py all` 告警） | 合成一个，保留触发词更全的名字；另一份内容并入后删目录 |
| ③ 新建 | 三问全中 **且** 与现有技能覆盖 <28% | `skill-creator` 建，实体 `<技能目录>/`；建完必须跑 `overlap_check.py all` 确认没撞车 |
| ④ 不建技能 | 只是这个仓库的约定 / 一次性偏好 | 前者写项目 `MEMORY.md`，后者写用户级 `MEMORY.md` |

### 建前查重（可量化，别凭感觉）

```bash
python scripts/overlap_check.py candidate "一句话职责" --triggers "触发词1, 触发词2"
python scripts/overlap_check.py all                 # 现有技能两两重叠 + 告警
python scripts/overlap_check.py all --gate          # 巡检用：有告警返回 1
```

判定口径：**≥0.50 已被覆盖 → 优化它**；0.28~0.50 → 读那个技能的「边界」节，说得清"何时不用它"才允许新建；<0.28 → 可新建，但仍要确认触发词不撞车。

**注意**：脚本量的是"字面覆盖"，不是"能力覆盖"。分数低但你知道它其实干得了同一件事，就按事实判——别让工具替你思考。反过来，分数高更要停下来看，那通常意味着该改旧的不该建新的。

### 什么时候不说话

自检每次都做，**开口只在有结论时**。下列情形静默通过，一句都不提：

- 纯问答、概念解释、闲聊、查个数据看一眼文件；
- 任务一次性，没有可复用步骤；
- 已有技能完全覆盖，本次没新增任何约束或纠正；
- 台账里这个候选已提过并被拒；
- 用户明显在赶进度、连着下达新指令——记下，等 T2 或 T3 再提。

**别养成「每轮结尾都问一句」的习惯**，那不是自检，是噪音。

### 怎么落地：默认直接做，末尾告知一行

**发起权、决策权都在我这边。** 用户 2026-11-10 说得很直白：「不是我说了你才做，是你自己的」。2026-11-12 又补了一句「有用的正确的直接优化或创建就行」——**连"改现有技能要先问"这条也取消了**：判断够格就直接改、直接建，末尾一行说明，他只留事后否决权。

| 情形 | 动作 |
|---|---|
| 三问全中，新建技能或**优化现有技能** | **直接做**，做完在末尾告知一行；新建的附"不要就说删" |
| 三问全中，但证据只有一次（判得勉强） | 不建不做，记台账 `待定`；同类再出现一次就落地 |
| 用户明确说过不沉淀 | 台账标 `已拒`，**以后不再提**，除非他自己提起 |
| 判定不够格（一次性／通用能力／项目约定） | **静默跳过**，只在台账记一行理由，连"没有要沉淀的"都不说 |

告知格式就两行，别写小作文：

> 沉淀：这次跑通的 XX 流程已并进 `yyy`（改了哪几节）；下次同类直接走它。

> 沉淀：新建了 `xxx`（`<技能目录>\xxx`），不要就说删。

**为什么不问**：技能是磁盘文件，建错了一句"删了"就回滚；而每轮都问，用户会学会无视这句话，机制废掉。**真正的成本不是建错，是问太多。**

**动作必须可见**：新建说清路径与用途；改现有 SKILL.md 点明改了哪几节，让用户能一句话否掉。

**跳过也要留痕**：尤其"看着像但不够格"的候选，写进 `references/distill-ledger.md` 标理由——不留痕的代价是下次从零再判一遍。

**不做噪音**：一次会话里连续多个小任务，合并成一条沉淀说明。

T3 的定时部分有两条腿：会话内看 `scripts/selftick.py --status`（距上次巡检 >7 天就 `--audit`），跨会话靠每周自动化「技能提取与创建巡检」兜底（见 `references/distill-trigger.md`「定时」那节）。两者都只补漏，不替代 T1。钩子那半边若迟迟没出现 `<skill-match>` 块，查 `references/` 下的 hook-trace.log（首次触发后才生成）判断是没触发还是真无匹配，必要时跑 `install_hook.py` 重装并重启 WorkBuddy。

### 例外时才用的话术（一句话）

只在**我判得勉强、想留个证据**时才说；正常落地不用问。

> 这次跑通的 XX 流程以后还会碰到，要沉淀成技能吗？我建议并入 `yyy` 而非新建，因为骨架已经在了。

### 落地必做（缺一等于没建）

**新建前**：`overlap_check.py candidate` 查覆盖度 → 决定 优化／合并／新建。

**新建后**：建实体 → 建 junction → `quick_validate.py` → 注册「路由表」+「触发词」→ 加 `SELFTEST_CASES` 用例 → `refresh_index.py` + `match_skill.py --selftest` 全 PASS → **`overlap_check.py all` 确认没撞车** → 台账记一行。逐项清单见 `references/distill-trigger.md`。

## 反模式

| 不要做 | 原因 |
|---|---|
| 为"这是什么意思"这类纯问答加载技能 | 纯损耗，用户等更久 |
| 加载了技能却不用它的流程，凭记忆做 | 格式必然跑偏，等于白加载 |
| 同时加载两个互斥技能（如两份雅思技能） | 输出两套结构，互相打架 |
| 技能里的校验脚本跳过不跑 | `check_note.py` 之类的脚本正是防"看着对其实错" |
| 匹配不到就自己造一套新流程 | 先问一句"要不要按 X 来"，别自创 |
| 一有新流程就新建技能 | 技能库的熵增全是这么来的：三个技能抢同一批触发词，之后每轮都要仲裁。先跑 `overlap_check.py` |
| 新建后不改旧技能的边界 | 两个技能都能干，等于两个都不该被选中；边界要写在各自 SKILL.md 里 |

## 维护

新增或改完任何技能，先跑完整性校验——它专治「文档里写了、文件其实没建」这种隐形坏点（frontmatter 缺字段、正文引用的脚本不存在、正文空壳）：

```bash
python "<技能目录>/scripts/quick_validate.py"
```

技能清单会变。新增或删除技能后，刷新索引：

```bash
python "<技能目录>/scripts/refresh_index.py"
```

脚本会重扫 `~/.workbuddy/skills` 与当前项目的 `.workbuddy/skills`，重写 `references/skill-index.md`，并列出**未在路由表中登记**的新技能——看到这种提示就把它补进上面的表。

改完路由表或「触发词」后，跑回归测试，确认没有把已有判定改坏：

```bash
python "<技能目录>/scripts/match_skill.py" --selftest
```

用例必须**全 PASS**（当前 25 条，只增不减）。发现新的错配，就把「原话 + 正确技能」加进 `scripts/match_skill.py` 的 `SELFTEST_CASES`，再调触发词——**先立靶再改枪**，否则调一个坏一个。

**否定断言**：期望值写成 `!技能名` 表示"top-1 不许是它"。中文长句里泛词几乎必然出现，正例只能证明"该中的中了"，证不了"不该中的没中"——`("对仓库进行补充", "!github")` 这种用例才是防回归的关键。抓到一个误判，先补否定断言让它 FAIL，再改门槛或触发词。

**与 `skill-creator` 的分工**（最容易搞混）：本技能管**判定**（该不该建、建在哪儿、要不要并入），`skill-creator` 管**执行**（真去建）。因此"值得做成技能吗 / 要不要沉淀"→ 本技能；"帮我建个新技能"→ `skill-creator`。区分靠语气：问句走判定，命令句走执行。脚本里的 `_looks_like_meta()` 实现了这条规则（名词 + 动作 + 判断语气或机制话题才兜底）。

`--list` 可打印当前生效的全部触发词，排查"为什么没命中"时先看它。

**改表后必须同步三处，否则会漂移**：

1. 本文件的「路由表」（完整版，含组合规则与仲裁）；
2. 用户级 `MEMORY.md`「零、开工前技能路由」那张快捷表（每会话自动注入，是最先被读到的入口）；
3. `references/skill-index.md`（跑脚本自动生成，不用手改）。

判断哪处该写：**新增技能**→三处都写；**只改触发词/边界**→本文件 + MEMORY.md 的"撞车仲裁"；**只是描述措辞变化**→只跑脚本。
